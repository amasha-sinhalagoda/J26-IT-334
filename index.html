Research Component — Probabilistic Landslide Forecasting

Reading landslide risk from soil, history and rain

A three-factor machine learning framework for the Nuwara Eliya highlands — built on the premise that where slopes have already failed teaches a model more than the angle at which they currently stand.

01 — Architecture

Full system architecture

The complete path from raw datasets to a village-facing alert, in one view: three input datasets, the spatial processing layer that fuses them, the classifier, the explainability layer, and the two things that actually leave the system — a risk score and a map.

02 — Position

The methodological bet

Most susceptibility models start from a Digital Elevation Model and derive slope angle as the primary predictor. This component reverses the emphasis: historical failure records become the backbone, with soil and rainfall layered on as the static and dynamic modifiers around them. A slope's angle is one fact about it; a slope's failure record is a fact about everything that made it fail.

Resolution

DEM data is too coarse

Freely available SRTM/ASTER elevation rasters sit around 30m resolution. A village-level, site-specific prediction needs finer granularity than a single elevation cell can offer across a whole hillside.

Causation

Slope angle is one variable of many

Failures at Walapane, Ambagamuwa and Kotmale are rarely angle alone — road cuts, building loads, soil saturation and land-use change compound with gradient. Angle-only models miss the human layer entirely.

Ground truth

History is the label, not a proxy

A historical inventory is literally the outcome the model is trying to predict, recorded at real sites. Training against it directly, rather than against a geometric proxy, is a shorter inferential distance to accuracy.

03 — Study Area

Three divisional secretariats, one highland catchment

The pilot zone sits inside Nuwara Eliya District's central highlands — steep tea-estate terrain with a long monsoon exposure window. Each of the three target divisions carries a different dominant risk signature, which is why the map below is colour-coded to the same factor palette used throughout this document.

04 — Mechanism

How the three factors connect

Soil supplies the static ceiling on how much saturation a slope can take before it gives way. Rainfall supplies the dynamic trigger that pushes toward that ceiling. History supplies the label the model is actually learning to predict, and the spatial pattern that tells the model which combinations of the other two have mattered before. All three are fused into one feature vector per grid cell before the classifier ever sees them.

Soil Type

Role
Static ceiling on saturation capacity and slip resistance.
Source
Digitized soil/geotechnical layers, Census & Statistics shapefiles, OSM building & road-cut features.
Method
QGIS digitization, clipped to the Walapane / Ambagamuwa / Kotmale pilot zones.
Feature output
Permeability class, shear-strength proxy, distance-to-road-cut.

Historical Landslides

Role
Ground-truth label and spatial-pattern prior — replaces the DEM/slope proxy.
Source
NBRO landslide portal records, DMC early-warning reports for the district.
Method
Spatial clustering and frequency-ratio weighting of confirmed failure points.
Feature output
Local failure density, nearest-event distance, recurrence weighting.

Rainfall

Role
Dynamic trigger — the variable that turns a stable slope into a failing one.
Source
Nearby NBRO rain-gauge network, live and historical readings.
Method
Spatial interpolation (IDW/Kriging) to grid cells, 3-day antecedent accumulation.
Feature output
Cumulative antecedent rainfall, live intensity threshold flag.
05 — Comparison

Where the two approaches actually diverge

Both approaches start from the same terrain and site data. The conventional path stops at geometry — an elevation raster reduced to a slope angle. This component's path continues into the record of what actually happened on that geometry, which is where soil, land-use and human factors leave their fingerprints.

06 — Pipeline

End-to-end, from raw records to a village alert

The framework above is the mechanism; this is the build order — the tools each stage actually runs on, from source data through to the Web-GIS interface a village-level user sees.

01
Ingest & digitize
Pull Census/Statistics shapefiles and OSM building/road data into QGIS; digitize the Walapane, Ambagamuwa and Kotmale pilot boundaries.
02
Spatially join
Load layers into PostgreSQL + PostGIS; run OSMnx extraction for road-cut proximity; interpolate rain-gauge readings onto the grid.
03
Engineer the feature matrix
Combine static soil/history features with dynamic antecedent-rainfall features into one row per grid cell per time step.
04
Train & validate
Fit XGBoost/LightGBM against the historical failure inventory as ground truth; validate on held-out events and non-failure sites.
05
Explain
Run SHAP over each prediction to produce the per-factor percentage breakdown behind a flagged grid cell.
06
Deploy & alert
Serve live risk layers through MapLibre GL JS, styled for high-contrast accessibility, with Sinhala/Tamil alerts via i18next.
